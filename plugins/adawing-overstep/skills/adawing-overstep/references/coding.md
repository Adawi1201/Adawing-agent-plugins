# 编码规模与编码纪律

编码任务在写 `[SCOPE]` 之前读取本文件：先按“编码规模”定档，把 tier 写进 `[SCOPE]`；之后写每一处代码时，按下文四条纪律与 SKILL.md 的“精准修改”执行。

## 编码规模

仅编码任务定档。定档前先查一次调用方：优先使用项目已有索引，没有索引时用文本或符号检索；调用方写到对外入口（Controller、路由、页面），不止最近一层。

三个规模判断：

- 是否跨模块边界
- 是否改公共接口：签名，或对外可观察的契约（接口返回内容 / 顺序、状态码、校验规则、持久化结果）；签名不变但契约变了也算。文案、样式不算
- 是否改数据形状

| 结果 | Tier | 阶段 | 细则 |
|---|---|---|---|
| 全否 | `direct` | (preview) -> build -> verify | [tiers/direct.md](tiers/direct.md) |
| 命中一项 | `planned` | plan -> (preview) -> 闸门 -> build -> review -> verify | [tiers/planned.md](tiers/planned.md) |
| 命中两项以上，或需求包含多个子功能 | `staged` | 同 planned，计划与验证落盘 | [tiers/staged.md](tiers/staged.md) |

tier 依据援引调用方和规模，不援引需求歧义。

**preview** 由验收方式决定，与 tier 正交。改变用户可见布局、交互或状态转移，验收依赖视觉或流程，或存在两个以上需要对照的用户状态时，不得跳过：

- `none`：diff 与测试足以验收；不读 preview reference
- `inline`：少量状态或输入输出即可表达；在对话中呈现，不新建文件
- `page`：多页面、多状态或高度依赖视觉 / 流程；生成一个入口页

`inline` 与 `page` 读 [phases/preview.md](phases/preview.md)。

## 编码纪律

### 最小实现

只实现用户要求的功能。不添加未要求的灵活性、可配置性或抽象。没有第二个使用场景，不抽象；没有第二个实现，不建接口。

原因：抽象的形状应当由第二个真实场景决定，只有一个场景时抽出的形状通常不对，之后还要改回来。

做法：

- 新增接口、基类、工厂、通用工具方法前，先数现有调用方和实现；达不到第二个，就写成具体代码
- 参数、配置项、开关只为用户提到的变化而加
- 同一个类中为可读性拆出的私有方法不算抽象，按现有代码的拆分粒度来

### 防御范围

只为跨越进程、网络、用户输入的真实边界做校验。对内部调用和理论边界不写兜底。添加兜底前，先指出真实业务触发路径；指不出就不加。

原因：每一处兜底都是一条要维护、要测试的分支。触发不了的分支只增加阅读成本和改动规模，还会掩盖真实错误。

做法：

- 边界包括：用户输入、外部接口返回、文件与网络读写、反序列化、进程间调用
- 内部调用方已保证的前置条件，不在被调用方再校验一次
- 新增 catch、重试、降级、加锁、并发保护前，在 build 报告中写出触发路径：什么输入或什么时序，经过哪条调用链，会走到这里
- 既有代码在同类位置已有的处理方式，按“沿用现有风格”照做

### 注释纪律

注释只写 WHY，不写变更史。禁止“曾经修复过”式叙事；禁止仅引用外部文档而不写明关键约束。

原因：注释描述的是代码现在为什么这样写；变更经过由 git 记录，读代码的人只需要当前的约束。

做法：

- 只在代码本身表达不出的约束处写注释，例如外部系统的限制、看似多余但必需的顺序、性能取舍
- 需要引用外部文档时，先把关键约束写进注释，引用只作补充
- 修 bug 时，注释和测试名描述正确行为，不描述出过的问题
- 注释密度与所在文件保持一致

### 沿用现有风格

修改前先读相邻代码。匹配现有命名、缩进、错误处理和注释密度。不因个人偏好重构无关代码。

原因：一个项目里的写法一致，读者才能靠模式理解代码。混入另一种风格的代码，即使写得更好，也会增加理解成本。

做法：

- 动手前读目标文件，以及同目录或同层的一个相似文件
- 对齐：命名方式、错误处理与日志写法、空值处理、导入顺序、测试结构、注释语言与密度
- 现有风格与你的偏好不同时，沿用现有风格；认为现有写法有缺陷时，新代码仍保持一致，在 `[REPORT]` 中提一句，不顺手改
- 不运行会改动无关行的格式化命令；需要格式化时只作用于本次改动的行
