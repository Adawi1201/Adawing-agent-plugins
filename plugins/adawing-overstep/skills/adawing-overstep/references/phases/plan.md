# plan 阶段

plan 把 `[SCOPE]` 已确定的请求和取舍转换为可执行、可验证的任务，不重新承担需求发散或方案选型。

## 输入

- `[SCOPE]` 和用户已经确认的要求
- tier、调用方检索结果和当前工作区状态
- 目标文件、相关接口、测试与构建入口的实际内容

信息不足时先检索。只有缺口会改变验收结果时才转 `[CLARIFY]`；能由仓库证据确定的内容不交给用户判断。

## 任务拆分

每个任务是可单独审查、单独验证的最小交付单元，写清：

- 创建、修改、测试和文档文件的精确路径
- 使用和产生的接口、符号或数据形状
- 行为的前后差异与验收条件
- 对应的用户请求项
- 实施顺序、增量验证命令和预期结果

整个计划另写：

- 回滚方式（整体一处，不按任务重复）
- Non-Goals：本轮明确不做的内容

每个任务都要对应到 `[SCOPE]` 的某一项请求；对不上的任务不进入计划。设置、配置和文档并入真正需要它们的任务，不为凑步骤单独拆分。禁止 `TBD`、`TODO`、“增加适当处理”、“写相关测试”和“同上”等不可执行占位。

## 深度

`planned` 在对话中给出计划，覆盖上述信息但保持紧凑，不创建文件。

`staged` 写入 `docs/adawing/plans/YYYY-MM-DD-<topic>.md`。只在代码片段能消除接口或行为歧义时写片段，不复制大段现有代码。

## 自检

计划完成后检查：

1. 每项请求都有对应任务，每个任务都对应到请求
2. 路径、符号、类型和任务间接口一致
3. 没有残留占位、重复任务或超出 Non-Goals 的内容
4. 每个任务都有可执行的验证

发现问题直接修正计划。需要改变 `[SCOPE]` 已确定的请求或取舍时，停下并回到入口，不在 plan 中静默改方案。
