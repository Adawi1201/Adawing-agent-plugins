# build 阶段

build 按已确认的范围实施改动，在影响面扩大或证据不成立时及时停下。它不重新决定需求，也不负责提交分支。

## 开始前

- 读取 `[SCOPE]` 与 plan（`direct` 只有 `[SCOPE]`）
- 记录任务开始时的 commit（`git rev-parse HEAD`），供 scope-check 使用
- 检查 git 状态，识别并保留用户已有改动
- 读取目标文件及其调用方，再读同目录或同层的一个相似文件，确定现有风格；不凭文件名猜实现
- 确认本轮要做的最小独立任务和对应的增量验证

## 执行循环

对每个独立任务依次执行：

1. 只编辑当前任务需要的文件，按 [../coding.md](../coding.md) 写代码
2. 立即运行最相关、成本最低的增量验证
3. 阅读结果，确认失败或通过的真实含义
4. 对照 diff 检查：每一处改动都能对上请求项，没有意外格式化，没有覆盖用户改动
5. 记录证据后再进入下一个任务

不先批量改完再统一验证。

新增 catch、重试、降级、加锁或并发保护时，在本阶段报告中写出它的业务触发路径。写不出就不加。

## 范围变化

- 需要修改清单外文件：先输出 `[RESCOPE]`，说明原因并更新清单
- 新增影响命中更高 tier：输出 `[RESCOPE]`，立即升档，补做缺失阶段
- 计划中的路径、接口或验证命令不存在：暂停当前任务，修正 plan
- 同一方案连续失败两次：停止重试，报告证据，回到入口
- 验证暴露新的独立缺陷：记录在 `[REPORT]` 的“未完成或偏离”中，不在当前任务中扩展范围

工具退出成功只说明工具执行成功。代码行为是否正确，由对应的测试、构建或运行时证据判断。

## 完成 build

报告实际修改的文件、每个增量验证的结果和范围变化，然后进入 review（`direct` 进入 scope-check），不直接声称任务完成。
