# verify 阶段

verify 把本轮真实证据映射到验收条件，并输出 `[REPORT]`。没有运行的检查不能写成通过，历史结果不能代替本轮结果。

## 选择检查

从项目已有命令和 plan 的验收条件中选择：

- 静态检查：lint、类型检查、格式检查
- 自动测试：最小相关测试，再按风险决定是否扩大
- 构建：编译、打包或生成产物
- 运行时验证：认证、Filter、路由、部署健康检查、交互等不能由编译证明的行为
- 用户手动验证：只能由用户环境或主观验收完成的内容

## 证据要求

每项报告：

- 实际命令或操作
- 结果与退出状态；失败时给出关键摘要
- 该证据覆盖的验收条件
- 未运行项及原因

不用“应该”“看起来”代替证据。某项失败时修复后重新验证，或如实报告未通过；不用其他检查的成功覆盖失败。

## [REPORT] 中的验证项

分别报告，不压缩成笼统的“完成”：

```text
代码修改：已完成 / 未完成
自动验证：通过 / 部分通过 / 未运行
运行时验证：通过 / 未通过 / 未运行
用户手动验证：已确认 / 待确认 / 不适用
```

自动与运行时验证都有本轮证据时，可以报告实现已完成；仍需用户手动验收时，明确标注产品验收待确认。

## 越界与偏离

review 的保留项、scope-check 中合理追加的文件、build 中记录的新缺陷，全部汇入 `[REPORT]`：

- **越界**：未要求的功能、抽象、防御、文件或格式改动
- **未完成或偏离**：没做到的请求、与指令不一致的做法、对指令所做的解释

有任一项时，请用户确认保留还是撤回，并停在这里。

## 产出深度

`direct` 与 `planned` 在对话中紧凑报告。`staged` 另写 `docs/adawing/verify/YYYY-MM-DD-<topic>.md`，对话中仍只给 `[REPORT]` 和关键证据，不复制整份报告。
