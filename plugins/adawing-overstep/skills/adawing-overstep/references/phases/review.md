# review 阶段

review 在 build 之后、verify 之前审查实际 diff，找出越界和偏离，并在报告前处理掉。写代码时看的是正面做法（[../coding.md](../coding.md)）；本阶段对照的是这些做法没守住时 diff 里会出现的样子。

## 先跑 scope-check

在仓库根目录运行：

```bash
node <本 skill 目录>/scripts/scope-check.mjs --base <任务开始时的 commit> <[SCOPE] 与 [RESCOPE] 声明的文件...>
```

- 文件参数只来自事先声明的清单，不在对账时补入
- 退出码 1 表示存在清单外文件：逐个说明，属于越界的撤回，属于合理追加的补一条 `[RESCOPE]`，并在 `[REPORT]` 的“越界”中列出
- `flags` 是脚本按关键词标出的可疑行，有误报；逐条判断，确属越界的修正，不属于的在报告中一句话说明
- 任务开始前已存在的未跟踪文件也会被列出，按原有状态说明即可

## 对照 diff 检查

逐项检查，每项都对照 diff 中的具体位置。

**请求范围**

- 存在对不上任何请求项的改动块
- 顺手优化了相邻代码，删除了与本任务无关的死代码，或重新格式化了无关行
- 新增了用户没要求的功能、参数、配置项或开关

**抽象**

- 新接口只有一个实现
- 新的抽象类、工厂、策略、通用工具方法只有一处调用
- 为“以后可能”预留的扩展点、泛型参数或钩子

**防御**

- 对内部调用方已保证的数据再次校验，或同一数据在多层重复校验
- 新增的 catch、重试、降级、锁、并发保护说不出业务触发路径
- 为理论上的竞态或极端输入增加的分支，用户没有要求

**注释与文档**

- 注释叙述变更经过：“修复了……问题”“之前是……现在改为……”“为解决 xx bug”
- 注释只写“见设计文档”“按方案 B”，没有写出关键约束
- 注释或代码中出现决策记录、方案对比、用户要求的转述
- 新建了用户没要求、本 skill 也没规定的记录类文件：变更对比、决策归档、总结报告

**风格**

- 新代码的命名、错误处理、日志、空值处理、导入顺序或注释密度与所在文件不一致
- 把现有写法改成了自己偏好的写法，而这不在请求范围内

**行为与一致性**

- 调用方、公共接口、类型和数据形状是否同步
- 测试、文档和配置是否与实现一致
- 是否遗漏运行时验证或安全门控，是否把构建通过当成行为正确

## 处理结果

范围内、不改变已确认行为的修正直接处理，然后重跑对应的增量验证。需要改变接口、数据形状、计划或 tier 的问题不在 review 中暗改，回到相应阶段。

报告发现、已修正项和保留项。保留项进入 `[REPORT]` 的“越界”或“未完成或偏离”。没有发现时明确写“无 review 发现”。
