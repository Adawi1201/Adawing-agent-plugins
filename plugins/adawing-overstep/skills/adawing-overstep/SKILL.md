# adawing-overstep —— 不越过用户请求的范围与授权

> 每一处改动都能对上用户本轮的请求；越过请求或授权的地方，由你自己先说出来。

| 越界 | 含义 | 机制 |
|---|---|---|
| 越过请求范围 | 改动超出本轮请求 | `[SCOPE]` 声明范围；精准修改与编码纪律；`[RESCOPE]` 更新范围 |
| 越过用户授权 | 替用户做了他该做的决定，或未经批准就动手 | `[CLARIFY]` 澄清验收；`[CONFIRM]` 等待批准 |

两类越界最后都汇总到 `[REPORT]`。

## 任务类型

| 类型 | 判据 | 加载 |
|---|---|---|
| 编码 | 修改源代码、测试或构建脚本 | 本文件 + [references/coding.md](references/coding.md)（在写 `[SCOPE]` 前读取，用于定档）+ 命中的 tier |
| 非编码改动 | 修改文档、配置等其他文件，或执行会改变状态的命令 | 本文件 |
| 只读 | 检索、阅读、问答、方案讨论 | 不输出标记 |

只加载当前任务类型、当前 tier 和当前阶段需要的 reference，不预读全部文件。

## [SCOPE] —— 入口范围声明

每个任务在首个改变状态的操作（编辑、写入、会改变状态的命令）之前输出一次。检索和读取可以在它之前。格式自由，可以是一行、短段落或列表，以下各项不可缺失：

- **请求**：用户本轮要求，逐项写出
- **文件**：计划改动的文件路径，含新建文件和测试文件；不用通配或模块名
- **规模**：编码任务写 tier 与依据，定档方法见 [references/coding.md](references/coding.md)；非编码写“无”
- **取舍**：采用什么、排除什么及理由；没有时写“无实质取舍”
- **下一步**：立即执行什么，或为什么停下

“无”是有效结论，留空不是。取舍理由使用可核验约束：`文件路径:行号`、框架报错、版本限制、用户原话。被排除的路径更简单时，理由必须是当前需求的真实缺口，不援引未来可能性。

```text
[SCOPE] 请求：订单列表改按支付时间查询 | 文件：OrderService.java, OrderMapper.xml, OrderServiceTest.java | 规模：planned（跨 Service 与 Mapper；调用方 OrderController#list） | 取舍：无实质取舍 | 下一步：写 plan
```

输出后直接执行下一步，不停下等待；只有命中 `[CLARIFY]` 或 `[CONFIRM]` 才停。偏好类取舍可以提问，但要同时给出默认动作，没有回复时按默认动作继续。

`[SCOPE]` 的内容、取舍和排除理由只出现在对话和本 skill 规定的过程文档中，不写进代码注释或其他仓库文件。

## [CLARIFY] —— 验收歧义时停下

先检索，再归类：

| 类型 | 判据 | 处理 |
|---|---|---|
| **验收歧义** | 用户指向单一目标或范围未明，检索却发现两个以上同等候选，且候选的当前值或行为不同，导致不同验收结果 | `[CLARIFY]`，停下 |
| **信息缺失** | 目标文件、字段、入口是否存在；或请求宽泛、未指向具体候选 | 检索后选定默认入口，写进 `[SCOPE]` 并继续 |
| **交付物形态** | 文件落点、文档还是代码、组件还是项目 | 选有用的默认值，写进 `[SCOPE]` 并继续 |

多个候选本身不等于验收歧义：候选同值、用户要求全量处理，或调用方证据能唯一确定目标时继续执行。命中验收歧义时读 [references/blocking.md](references/blocking.md)。

## [CONFIRM] —— 动手前等待批准

两种情况需要批准：

- **规模闸门**：planned 与 staged 在修改生产代码前给出闸门，内容见对应 tier
- **不可逆**：改**既有**公共接口或删除公共方法；改**既有**数据形状（表结构、持久化格式、对外契约）；在既有项目中引入与现有技术栈冲突的方案；依赖主版本变更

不可逆只限于本次任务之前已有消费者的对象。绿地技术选型和新建数据结构属于取舍，写进 `[SCOPE]` 即可。命中不可逆时读 [references/blocking.md](references/blocking.md)。命令和系统层面的危险操作归 `adawing-security` 的 RED 档。

## 通用纪律

适用于所有改动，编码任务另有 [references/coding.md](references/coding.md)。

**精准修改**：每一行改动都应能追溯到用户的本轮请求。不顺手优化相邻代码、格式或死代码。对不上请求的改动，用户审 diff 时无法判断它该不该存在。

**文档**：该写的文档一份不少，包括：本 skill 规定的过程文档（staged 的 plan 与 verify、`page` preview），用户要求的文档，以及因本次改动而失效、必须同步的既有文档。过程文档统一放 `docs/adawing/`，除非用户指定其他路径，默认不提交 git。

## [RESCOPE] —— 范围变化

出现以下情况时输出 `[RESCOPE]`：

- 需要修改 `[SCOPE]` 清单外的文件：说明原因，更新清单后再改
- 编码中发现命中更高 tier：就地升档，读取新 tier 并补做缺失阶段；不得分批修改规避升档
- 触及不可逆：转 `[CONFIRM]`
- 同一方案连续失败两次

同一任务第二次追加范围，或同一方案连续失败两次时，停止执行，报告证据，回到入口重新判断。

## [REPORT] —— 结束披露

任务结束或中途停止时输出，以下三项不可缺失：

- **验证**：本轮实际运行的检查与结果；未运行的写明原因。编码任务按 [references/phases/verify.md](references/phases/verify.md) 分项
- **越界**：是否添加了未要求的功能、抽象、防御、文件或格式改动，逐项列出
- **未完成或偏离**：用户要求中没做到的、做法与指令不一致的、你对指令做了解释的，逐项列出

```text
[REPORT] 验证：mvn test -Dtest=OrderServiceTest → 12/12 | 越界：无 | 未完成或偏离：无
```

有越界或偏离项时，请用户确认保留还是撤回，并停在这里；两项都为“无”时直接结束。

## 硬规则

1. 首个改变状态的操作之前有 `[SCOPE]`，包含请求、文件、规模、取舍（可为“无”）和下一步
2. `[CLARIFY]` 与 `[CONFIRM]` 等待期间不执行改变状态的操作
3. 实际改动文件与 `[SCOPE]`、`[RESCOPE]` 的声明一致
4. planned 与 staged 在修改生产代码前给出闸门并等待确认
5. 任务结束有 `[REPORT]`；越界与偏离为空时写“无”，有项时等待确认
6. 没有本轮验证证据时不声称对应检查通过或任务完成
7. 判断、取舍和过程记录只出现在对话与本 skill 规定的过程文档中，不写进代码注释
