# adawing-guidance —— AGENTS.md 初始化生成器

为项目生成一份高性价比的 AGENTS.md。核心原则：**只写模型从代码里推断不出来、又不会频繁变化、且几乎每个任务都用得上的信息。**

## 工作流程

### 第一步：调研项目（只读，不改代码）

按以下顺序收集信息，每一项都要有证据来源，**禁止编造**：

1. **技术栈与版本**：读取 `package.json`、`pom.xml`、`build.gradle`、`requirements.txt`、`pyproject.toml`、`go.mod`、`Cargo.toml`、`composer.json` 等依赖清单中实际存在的文件
2. **构建/测试/运行命令**：读取 `Makefile`、`package.json` 的 scripts、`justfile`、CI 配置（`.github/workflows/`）、README 中的命令段落
3. **目录结构**：列出顶层目录，识别模块划分与入口文件（`tree -L 2` 或等效命令）
4. **既有约定**：读取 lint/format 配置（`.eslintrc`、`.editorconfig`、`checkstyle.xml` 等）、已有 `AGENTS.md`/`CLAUDE.md`/`.cursorrules`
5. **无法从文件确认的信息**（部署方式、冻结目录、业务术语等）：向用户提问，不要假设

### 第二步：组织内容

按稳定度从高到低排列七层（稳定度排序 = 缓存命中友好度排序）：

1. 项目定位与技术栈（一句话定位 + 框架和版本号）
2. 模块地图（职责边界 + 依赖方向，不罗列文件清单）
3. 可执行命令（构建、测试、启动、检查，必须真实可跑）
4. 非默认的代码约定（只写项目特有的）
5. 行为约束（何时提问、何时禁止提交等，每条一行）
6. 红线与禁区（冻结目录、密钥处理等）
7. 领域术语表（业务黑话与代码实体的映射）

详细的内容取舍标准、负面清单和写法示例见 [references/content-guide.md](references/content-guide.md)。

### 第三步：套用模板生成

以 [assets/AGENTS.template.md](assets/AGENTS.template.md) 为骨架，用调研结果替换占位符。

**生成规则：**

- 体量控制在 100～300 行（约 2k～6k tokens）
- 没有任何一层允许为空壳——收集不到有效信息的层直接删除该层，不要留"待定"
- 所有命令必须来自第一步的证据；不确定的命令标注后向用户确认
- 禁止出现：时间戳、"最近更新"、当前进度、临时 TODO、文件/类全量清单、教程式背景、模型已知的通用知识
- 规则写成祈使句，每条一行，不写解释

### 第四步：自检与交付

生成后逐条执行验收：

- [ ] 每条内容都能通过测试："没有这一条，模型会不会犯错或浪费一轮以上？"
- [ ] 所有命令在调研中有出处
- [ ] 无时间戳、无易变状态、无文件清单
- [ ] 七层按稳定度排序
- [ ] 总行数 ≤ 300 行

若项目中已存在 AGENTS.md，改为增量更新模式：保留有效内容，删除违反负面清单的内容，补齐缺失层，并向用户说明每处改动理由。

## 大型项目的分层建议

若项目是 monorepo 或模块差异大，建议采用"根 AGENTS.md + 模块目录局部 AGENTS.md"：根文件只放全局七层内容，模块特有约定就近放在模块目录下，避免局部修改击穿全局前缀缓存。
