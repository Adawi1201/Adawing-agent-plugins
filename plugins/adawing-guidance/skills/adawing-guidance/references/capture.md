# 沉淀模式

把任务中真实发生过的项目特有错误，整理成一条待用户确认的 AGENTS.md 规则。沉淀的规则会作用于之后的每个任务，固化错了的代价比犯一次错更大。

判断问题：**一个月后，在一个不相关的任务里读到这条规则，它还对吗、还有用吗？**

## 触发

- 用户纠正了你在本项目特有问题上的做法
- 同一个项目特有的错误在一次会话中出现第二次
- 用户要求“记下来”“写进 AGENTS.md”“以后别这样”

模型的通用问题（过度防御、注释写变更史、风格不一致等）不触发沉淀，它们由 agent 自身或已安装的 skill 管理。

## 该沉淀：四条同时满足

| 条件 | 判据 | 反例 |
|---|---|---|
| 项目特有 | 换一个项目就不成立 | “不要写过度防御”是通用问题 |
| 推断不出来 | 读仓库得不到，或要试错几轮、实际运行才能发现 | 依赖版本在 `pom.xml` 里写着 |
| 长期成立 | 与具体任务、当前进度无关 | “迁移期间先别改 v1 接口” |
| 会再遇到 | 一般任务都可能踩到，且已真实发生 | 只在某次特殊排查中出现 |

满足条件的通常是：

- **命令陷阱**：看着对、实际不对的命令，或必需的运行前提
- **环境前提**：服务、数据、配置必须先就绪
- **工具拦不住的约定**：在 review 中被打回的写法
- **禁区**：生成代码、冻结目录、不可手改的文件
- **跨模块联动**：改 A 必须同步 B
- **术语映射**：业务说法与代码实体的对应

## 不该固化

| 类型 | 原因 | 去处 |
|---|---|---|
| 本次任务的决定（“这次舍入用 HALF_UP”） | 一次性取舍，固化后会与用户以后的决定冲突 | 代码与提交信息 |
| 针对单个任务的临时指令（“先别动测试”） | 只在当时成立 | 不保存 |
| 当前状态：进度、已知 bug、临时绕过、迁移中间态 | 会过期，过期后误导 | 任务跟踪系统 |
| 根因未确认的经验（“好像要先 clean 才能编过”） | 会把猜测变成规则 | 先查清根因，再按四条判断 |
| lint、CI、类型系统已拦住的规则 | 重复 | 不写 |
| 仓库里直接能读到的信息 | 模型自己会读，除非它本身就是陷阱 | 不写 |
| 模型的通用缺陷 | 每个项目各写一遍，规则分散 | 由 agent 或 skill 管理 |
| 错误或决策的经过（“曾经因为 X 出过问题”） | 只需要约束本身 | 改写成约束 |
| 个人偏好 | 不适用于团队其他成员 | `CLAUDE.local.md` 或个人全局文件 |

能改代码或配置让错误不可能发生的（加测试、加 lint 规则、加 hook），优先建议那样做，而不是写一条提示词。

## 写法

- 一行祈使句，写约束本身；原因不自明时，同一行加一句原因
- 放进 [content-guide.md](content-guide.md) 对应的层
- 不带日期，不写经过

```text
好：单测用 `pnpm test:unit`：`pnpm test` 含 e2e，需要先启动 api 服务
坏：之前跑 pnpm test 一直失败，后来发现是 e2e 需要服务，所以以后用 test:unit
```

## 流程

1. 在任务结束时提出候选，不中断当前任务
2. 给出候选规则、放入的层、它满足四条件的依据（对应的那次错误）
3. 检查 AGENTS.md 中是否已有相关或矛盾的条目；有就改写已有条目，不追加矛盾的新规则
4. 用户确认后写入；用户拒绝的不再重复提出

```text
[沉淀候选] 层：常用命令
规则：单测用 `pnpm test:unit`：`pnpm test` 含 e2e，需要先启动 api 服务
依据：本次运行 `pnpm test` 因 e2e 连接 api 失败，用户纠正为 test:unit
冲突：AGENTS.md 第 18 行写的是 `pnpm test`，建议改写该行
```

写入后总行数超过 200 时，先按 [audit.md](audit.md) 精简，再写入。
