# AGENTS.md 内容取舍指南

## 目录

- 七层内容详解

- 缓存经济学背景

## 七层内容详解

### 1. 项目定位与技术栈

**写什么**：一句话定位；语言、框架及**确切版本号**；关键中间件。
**为什么**：版本决定模型生成代码时用哪套 API（如 Spring Boot 2 vs 3 的 `javax`/`jakarta` 差异），且无法从单个文件可靠推断。

### 2. 模块地图

**写什么**：顶层目录的职责边界、模块间依赖方向、跨模块通信方式。
**不写什么**：文件清单、类清单——模型可以自己 ls/glob。
**为什么**：模块边界是模型跨文件操作时最容易违反的约束。

### 3. 可执行命令

**写什么**：构建、测试（含单测过滤语法）、本地启动、lint/检查。
**为什么**：单位 token 收益最高的内容。没有它，模型每轮都要猜命令、试错。
**要求**：必须真实可跑，从 Makefile/package.json/CI 配置中提取，禁止凭经验编造。

### 4. 非默认的代码约定

**写什么**：异常处理策略、日志规范、命名分层、数据库规范（如禁止物理删除）。
**不写什么**："写可读的代码""注意性能"这类模型默认就遵守的泛泛之谈。
**判断标准**：这条约定被违反时，你是否会在 code review 里打回？会才写。

### 5. 行为约束

**写什么**：何时必须停下来提问、何时禁止 git commit/push、验证要求。
**写法**：祈使句，每条一行，不写理由。

### 6. 红线与禁区

**写什么**：冻结/遗留目录、密钥与配置纪律、数据库迁移纪律。
**为什么**：这类错误的代价远高于普通 bug，需要显式"刹车"。

### 7. 领域术语表

**写什么**：业务术语与代码实体（表名、类名、字段名）的映射。
**为什么**：业务黑话是模型纯靠代码最难对齐的信息，几行消除大量误解。

## 负面清单（一律禁止写入）

| 内容 | 原因 |
|---|---|
| 当前进度、临时 TODO、最近修的 bug | 高频变化，每次修改击穿整个前缀缓存 |
| 时间戳、"最近更新于" | 同上，且对模型无价值 |
| 完整文件/类/接口清单 | 模型可自行探索，且迅速过时 |
| 长篇教程式背景介绍 | 每轮付费，稀释注意力 |
| README 式项目宣传 | 对 agent 零价值 |
| 模型已知的通用知识 | 如"React 是组件化框架" |

## 写法示例

**坏**：

```markdown
## 项目介绍
本项目是一个现代化的、采用微服务架构的订单管理系统，致力于为用户提供
高效便捷的订单处理体验。项目始建于 2023 年，经过多次迭代……
```

问题：宣传语、历史沿革、无版本号，全部是无法执行的废话。

**好**：

```markdown
## 项目概况
- 定位：订单中台后端，对外提供订单创建/查询/取消 API
- 技术栈：Java 17 + Spring Boot 3.2 + MyBatis-Plus 3.5 + MySQL 8 + Redis 7
```

**坏**：

```markdown
## 注意
请编写高质量的代码，注意边界情况。
```

问题：模型默认就会，零信息量。

**好**：

```markdown
## 代码规范
- 业务异常统一抛 BizException，禁止裸 catch
- 新表必须含 created_at/updated_at，禁止物理删除
```

## 缓存经济学背景（为什么这些规则成立）

AGENTS.md 作为固定前缀注入每轮对话，其成本模型：

- 前缀缓存按 token 序列**从头精确匹配**，任何修改使改动点之后全部失效 → 因此内容必须低频变化、按稳定度排序、批量修改；
- 即使按命中价（原价的约 10%）计费，前缀**每轮都在产生费用** → 因此必须控制体量，每条内容都要证明自身价值；
- 体量建议 2k～6k tokens：95% 命中下 5k tokens 每轮仅等价约 725 tokens，超过 10k 后边际收益通常转负。

验收金标准：**"没有这一条，模型会不会在实际任务中犯错或浪费一轮以上？"** 会就写，不会就删。
