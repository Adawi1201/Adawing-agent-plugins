# plan 阶段

plan 把 invoker 已确定的语义决定转换为可执行、可验证的任务，不重新承担需求发散或方案选型。

## 输入

- invoker 的 `[EVALUATION]` 和用户已经确认的要求
- tier、调用方检索结果和当前工作区状态
- 目标文件、相关接口、测试与构建入口的实际内容

信息不足时先检索。只有缺口会改变验收结果时才回到 invoker；能由仓库证据确定的内容不向用户转交判断。

## 任务拆分

每个任务应当是可单独审查、单独验证的最小交付单元，并写清：

- 创建、修改、测试和文档文件的精确路径
- 使用和产生的接口、符号或数据形状
- 行为的前后差异与验收条件
- 实施顺序、增量验证命令和预期结果
- 回滚方式
- Non-Goals

设置、配置和文档应并入真正需要它们的任务，不为凑步骤单独拆分。禁止 `TBD`、`TODO`、“增加适当处理”、“写相关测试”和“同上”等不可执行占位。

## 深度

`single` 使用行内计划，覆盖上述信息但保持紧凑，不创建文件。

`full` 写入 `docs/adawing/plans/YYYY-MM-DD-<topic>.md`。只在代码片段能够消除接口或行为歧义时写片段，不复制大段现有代码。

## 自检

计划完成后检查：

1. 每项已确认要求是否有对应任务
2. 路径、符号、类型和任务间接口是否一致
3. 是否残留占位、重复任务或超出 Non-Goals 的内容
4. 每个任务是否都有可执行的验证和回滚方式

发现问题直接修正计划。若需要改变 invoker 已确定的语义路径，停止并回到 invoker，而不是在 plan 中静默改方案。
