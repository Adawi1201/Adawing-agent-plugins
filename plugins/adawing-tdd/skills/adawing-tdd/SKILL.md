# adawing-tdd —— 用测试复现 bug、检测漂移

> 说“修好了”“没影响别的”之前，先让一条测试替你说。

测试不只是交付物，它是你手里最客观的验证工具。遇到下面两类问题时，先想到它：

| 问题 | 靠自报的风险 | 用测试怎么做 |
|---|---|---|
| **bug 根因** | 读代码“看起来是这里”，修完无从证明 | 写一条在修复前失败的测试，红灯就是根因复现证据 |
| **漂移** | 实现偏离验收条件、顺手改坏旁边的行为、改动超出声明文件 | 验收条件转成断言（行为漂移）；跑既有测试（回归漂移）；`git` 对账（范围漂移） |

## 前提

本 skill 挂在 `adawing-workflow` 的阶段上，与 `adawing-invoker`、`adawing-workflow` 同装。它只增加证据要求，不改变 invoker 的路径判断和 workflow 的 tier、闸门。

加载本 skill 时若尚未进入 workflow，先加载 `adawing-workflow` 完成定档，再按所得 tier 执行下文；本 skill 不替代 tier、plan 与 gate。唯一例外是用户明确处于某个阶段（如“现在进入 verify”），直接执行该阶段。

## 强度

开始前读仓库根目录的 `AGENTS.md` / `CLAUDE.md`，查找 `adawing-tdd:` 一行（即使它已在上下文中，也要确认），例如：

```text
adawing-tdd: bugfix=required feature=suggested micro=off
```

没有这一行时使用内置默认值：

| 任务 | 默认 |
|---|---|
| bug 修复（任何 tier） | `required` |
| single / full 的行为改动 | `suggested` |
| micro 的非 bug 改动、纯文档 / 配置 / 样式 | `off` |

- `required`：必须按下文循环取得红灯和绿灯证据，做不到时说明原因并改用复现命令
- `suggested`：默认执行；跳过时在 plan 或 gate 中写一行理由
- `off`：不要求，但 bug 修复仍需满足 invoker 的根因复现要求

用户在当前对话中的明确要求优先于上述设置。你不修改这一行。

在首个 `[TDD]` 行或 plan / gate 中写明生效强度与来源，跳过测试的理由必须基于该强度：

```text
[TDD] 强度：bugfix=suggested（来源：AGENTS.md）
```

## 各阶段要做的事

### plan / gate：把验收条件变成断言

gate 中每条“判定通过的条件”必须归入一类：

- **断言**：写成 `输入 / 前置 → 期望输出 / 状态`，并给出测试位置，例如 `OrderServiceTest#rejectsEmptyItems`
- **手动**：只能由人判断的（视觉、文案语气），写清验收方式

“功能正常”“体验更好”“性能提升”“表现一致”这类无法归类的条件，改写成可断言的形式（给出数值、输出或状态）；确实只能人判的，拆成具体的手动检查项。gate 中不保留未归类条件，确认后的轮次同样适用。转不成断言，往往说明验收条件本身还没想清楚。

gate 同时声明本次允许改动的文件清单，供 verify 对账。清单包括将新增或修改的测试文件；一次性复现脚本放在仓库外（如 `/tmp`），否则也列入清单。

### build：先红后绿

1. **红**：先写测试，用项目自己的测试命令运行，确认它**在断言处失败**
2. **绿**：写最少的实现让它通过
3. 重复，直到每条断言都有对应测试

红灯的有效性是整个方法的关键：

- 编译错误、导入失败、找不到类不是红灯，说明测试还没跑到断言；补最小桩后重跑
- 修改前就通过的测试没有复现问题，也没有约束新行为，重写它
- bug 修复的红灯失败信息应当对应用户报告的现象

项目没有测试框架、且引入框架超出本次范围时，写一条可重复执行的复现命令（脚本、`curl`、CLI 调用）代替，同样要求先观察到错误输出，再观察到正确输出。

### verify：三层漂移对账

| 层 | 检查 | 证据 |
|---|---|---|
| 行为漂移 | 每条断言对应的测试本轮通过 | 测试命令与通过输出 |
| 回归漂移 | 受影响模块的既有测试本轮通过 | 测试命令与通过输出 |
| 范围漂移 | 实际改动文件都在 gate 声明清单内 | `drift-check` 输出 |

范围对账在仓库根目录运行，文件路径相对仓库根：

```bash
node <本 skill 目录>/scripts/drift-check.mjs --base <任务开始时的 commit> <声明的文件...>
```

传入的文件必须是 gate 声明时的清单原样，不在对账时补入文件。退出码 1 表示存在清单外文件：逐个说明原因，属于越界的撤回，属于合理追加的按 workflow 棘轮处理并在报告中标为“清单外追加”。任务开始前已存在的未跟踪文件会被列出，按原有状态说明即可。

没有 gate 的 micro 任务，以 build 前声明的改动文件为清单。

## 证据格式

在 build 和 verify 报告中，每条测试证据写成：

```text
[TDD] <测试名>  红: <失败的断言行>  绿: <本轮运行命令> → <通过数>/<总数>
```

没有红灯记录的测试不能作为“复现”或“约束新行为”的证据，只能算回归测试。

## 硬规则

1. `required` 强度下，没有红灯证据不修改生产代码
2. 红灯必须是断言失败，编译 / 导入 / 运行器错误不算
3. 不通过削弱、删除或跳过断言来换取绿灯；确需修改断言时说明原因
4. 强制失败的占位测试（`assert False`、`expect(true).toBe(false)`）不留到 build 结束
5. 绿灯必须是本轮新鲜运行结果，不引用历史输出
6. drift-check 的文件参数只来自事先声明的清单
