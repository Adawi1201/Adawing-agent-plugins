# adawing-tdd —— 用测试复现 bug、检测偏差

> 说“修好了”“没影响别的”之前，先让一条测试替你说。

测试不只是交付物，它是你手里最客观的验证工具。遇到下面两类问题时，先想到它：

| 问题 | 靠自报的风险 | 用测试怎么做 |
|---|---|---|
| **bug 根因** | 读代码“看起来是这里”，修完无从证明 | 写一条在修复前失败的测试，红灯就是根因复现证据 |
| **偏差** | 实现偏离验收条件，或顺手改坏旁边的行为 | 验收条件转成断言（行为偏差）；跑既有测试（回归） |

改动文件是否超出声明范围，由 `adawing-overstep` 的 scope-check 负责，本 skill 不重复。

## 前提

本 skill 挂在 `adawing-overstep` 的阶段上，必须与它同装。它只增加测试证据要求，不改变 overstep 的 `[SCOPE]`、tier 与闸门。

加载本 skill 时若尚未输出 `[SCOPE]`，先按 `adawing-overstep` 完成入口与定档，再按所得 tier 执行下文。唯一例外是用户明确处于某个阶段（如“现在进入 verify”），直接执行该阶段。

## 适用范围

| 任务 | 要求 |
|---|---|
| bug 修复（任何 tier） | 必须按下文循环取得红灯和绿灯证据；写不成测试时说明原因，改用可重复的复现命令 |
| planned / staged 的行为改动 | 默认按下文循环执行；跳过时在 plan 或闸门中写一行理由 |
| direct 的非 bug 改动、纯文档 / 配置 / 样式 | 不要求测试，不因本 skill 增加流程 |

用户在当前对话中的明确要求优先于上表。

## 各阶段要做的事

### plan / 闸门：把验收条件变成断言

闸门中每条“判定通过的条件”必须归入一类：

- **断言**：写成 `输入 / 前置 → 期望输出 / 状态`，并给出测试位置，例如 `OrderServiceTest#rejectsEmptyItems`
- **手动**：只能由人判断的（视觉、文案语气），写清验收方式

“功能正常”“体验更好”“性能提升”“表现一致”这类无法归类的条件，改写成可断言的形式（给出数值、输出或状态）；确实只能人判的，拆成具体的手动检查项。闸门中不保留未归类条件，确认后的轮次同样适用。转不成断言，往往说明验收条件本身还没想清楚。

将新增或修改的测试文件列入 `[SCOPE]` 的文件清单。一次性复现脚本放在仓库外（如 `/tmp`），否则也列入清单。

### build：先红后绿

1. **红**：先写测试，用项目自己的测试命令运行，确认它**在断言处失败**
2. **绿**：写最少的实现让它通过
3. 重复，直到每条断言都有对应测试

顺序本身就是要求，不能用等效结果代替：

- 红灯必须在**尚未改动的生产代码**上观察到。看到红灯之前，不编辑本条断言涉及的生产代码（下文的最小桩除外）
- 不先写实现、再回退或故意改坏代码去“补”红灯；即使最终测试、实现与输出都一样，也算顺序颠倒
- 已经先改了实现时，在 `[REPORT]` 的“未完成或偏离”中如实写明顺序颠倒；之后写的测试只算回归测试，不作为复现或约束新行为的证据

红灯的有效性是整个方法的关键：

- 编译错误、导入失败、找不到类不是红灯，说明测试还没跑到断言；补最小桩后重跑
- 修改前就通过的测试没有复现问题，也没有约束新行为，重写它
- bug 修复的红灯失败信息应当对应用户报告的现象

项目没有测试框架、且引入框架超出本次范围时，写一条可重复执行的复现命令（脚本、`curl`、CLI 调用）代替，同样要求先观察到错误输出，再观察到正确输出。

### verify：行为与回归

| 检查 | 内容 | 证据 |
|---|---|---|
| 行为偏差 | 每条断言对应的测试本轮通过 | 测试命令与通过输出 |
| 回归 | 受影响模块的既有测试本轮通过 | 测试命令与通过输出 |

结果写入 `[REPORT]` 的验证项。

## 证据格式

在 build 和 verify 报告中，每条测试证据写成：

```text
[TDD] <测试名>  红: <失败的断言行>  绿: <本轮运行命令> → <通过数>/<总数>
```

没有红灯记录的测试不能作为“复现”或“约束新行为”的证据，只能算回归测试。

## 硬规则

1. 需要红灯证据的任务，看到红灯之前不修改对应的生产代码；让测试能跑到断言的最小桩除外，桩不得实现目标行为
2. 红灯必须在未改动的生产代码上观察到；先实现再回退或改坏代码得到的失败不算红灯
3. 红灯必须是断言失败，编译 / 导入 / 运行器错误不算
4. 不通过削弱、删除或跳过断言来换取绿灯；确需修改断言时说明原因
5. 强制失败的占位测试（`assert False`、`expect(true).toBe(false)`）不留到 build 结束
6. 绿灯必须是本轮新鲜运行结果，不引用历史输出
